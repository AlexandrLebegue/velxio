## 1. Conclusion pour la revue

Une façade de **six outils** est plausible : `search_catalog`, `get_reference`, `save_project`, `check_project`, `build_project`, `read_artifact`. Elle nécessite un stockage local versionné à ajouter et un adaptateur vers la compilation REST existante. Le MCP actuel n'est ni un stockage de projets, ni un moteur de simulation.

Le format natif `.vlx` est le meilleur point d'échange avec l'UI ; le petit format « circuit » Python du MCP est différent et ne doit pas devenir le modèle persistant. Le catalogue JSON doit être complété par les définitions de cartes et les ajouts du registre. Les capacités catalogue, compilation et simulation doivent rester distinctes.

Une vraie simulation AVR avec observation de pixels e-paper existe dans les tests locaux. Cela justifie une piste ultérieure **limitée** pour `test_project`, mais aucun service générique instrumenté n'a été établi : conserver six outils pour le premier contrat. Ne jamais transformer un succès de compilation en succès de test.

## 4. Persistance, versions, chemins et concurrence proposés

Racine **nouvelle** `/app/data/mcp-compact/`, utilisant la persistance déjà déclarée, sans modification de configuration dans ce jalon. Sous cette racine : `projects/<opaque-id>/versions/<sha256>/project.json`, manifeste de tête, `builds/<build-id>/manifest.json`, `artifacts/<opaque-id>/...`. Ne pas écrire dans le cache compilateur comme stockage métier. Une racine de test temporaire sera injectée lors des tests ; aucun accès au vrai `/app/data` pour cette inspection.

1. Canonicaliser le JSON pour hasher le contenu (ordre des clés stable, tableaux conservés, nombres finis). Exclure l'horodatage d'export du hash métier, conserver les métadonnées séparément ; publier la règle. Aucun alias mutable `latest` accepté par check/build. Une version n'est jamais écrasée ; un nouveau save n'altère pas le build déjà admis.
2. Publier snapshot puis tête par fichiers temporaires uniques sur le même système de fichiers, `fsync` et remplacement atomique ; verrou par projet et comparaison `expected_version` sous verrou. Tests de crash avant/après publication. Verrou de fichier interprocessus pour les métadonnées si plusieurs transports/processus partagent la racine ; `asyncio.Lock` seul ne suffit pas.
3. Compiler dans **le processus propriétaire de la file existante**. Un SSE séparé et un backend partageant les mêmes variantes ne sont pas protégés par les verrous actuels. Avant tout futur déploiement multiprocessus, établir un propriétaire unique ou une exclusion interprocessus réelle ; aucun changement de topologie autorisé ici. Ne pas contourner la file en appelant directement le compilateur depuis le nouveau MCP.
4. Valider noms/IDs avant création : refuser absolus POSIX/Windows/UNC, NUL/contrôles, segments vides/`.`/`..`, séparateurs ambigus et doublons normalisés ; longueurs bornées. Vérifier aussi noms réservés, collisions casefold et collisions après aplatissement/renommage ESP-IDF. Fixer le sketch principal ; refuser l'ambiguïté de plusieurs `.ino` non résolue.
5. Calculer les chemins depuis des IDs serveur validés ; confinement par segments sous une racine résolue. Refuser les liens symboliques et traversées via un parent, y compris courses entre vérification et ouverture (`dirfd`/ouverture sans suivi ou primitive équivalente). Un simple `startswith` ne suffit pas. La lecture d'artefacts passe par leur manifeste, jamais par un chemin fourni.
6. Lier chaque build au hash projet, carte, ordre/point d'entrée normalisés, options/langage, SPIFFS, version de l'adaptateur, epoch/template, **versions et hashes réellement résolus** des bibliothèques et toolchain. Enregistrer la provenance ; si elle ne peut pas être figée, annoncer une reproductibilité limitée et ne pas partager un cache prétendument immuable. `available=true` et une liste de noms ne constituent pas un lockfile.
7. Timeout de réponse ≠ annulation du compilateur : exposer le job et continuer le polling borné. Respecter les protections existantes des répertoires partagés ; après redémarrage, un job interrompu devient état explicite `interrupted`, jamais succès inféré d'un fichier partiel. Pas de nouvelle commande d'annulation dans les six outils.

Bornes initiales **proposées, à valider en revue** : projet 2 MiB décodés au total (fichiers/SD/SPIFFS inclus), 128 fichiers, 256 KiB par source, 8 cartes, 512 composants, 1024 fils ; requête refusée avant matérialisation si dépassement. Artefact individuel 32 MiB, stockage dérivé global 256 MiB, 100 builds conservés, TTL dérivé 7 jours ; logs plafonnés à 1 MiB UTF-8 avec marqueur de troncature. Quota global snapshots 256 MiB, refus au dépassement, **pas de purge automatique des versions projet**. Les valeurs dépassant la limite doivent produire une erreur, jamais un firmware tronqué. Un firmware nécessitant plus de 32 MiB sera explicitement hors périmètre.

Les artefacts publiés restent immuables jusqu'à expiration ; publication d'un manifeste seulement après écriture complète et hash. Après purge : `artifact_expired` avec tombstone bornée, puis `not_found` après rétention de celle-ci. Purge sous verrou, sans supprimer versions projet, builds actifs ou lecture en cours. Le manifeste compact garde taille, hash, type et provenance. Les sorties de compiler peuvent contenir chemins internes : résumé nettoyé, aucun secret/configuration exposé automatiquement. Pas de garantie de sandbox de compilation apportée par cette inspection.
